# UI_SPEC.md — 画面仕様

## 1. 方針

- **Mobile First**。ダーツをしながら片手でも確認できることを重視する。
  390px 前後と 320px の両方で破綻しないこと。
- **残り点を入力したら、まず答えを見せる**（v1.2）。答えへ届くまでのタップ数だけでなく、
  スクロール距離・縦方向の占有面積・視線移動も減らす。
- PC でも DOM の順序（読み上げ順・スクロールの挙動）はスマートフォンと同じに保ち、
  64rem 以上では CSS だけで 2 列に並べ替える。CHECKOUT / SETUP は「答え・実戦入力」｜
  「他の候補」、TRAINING / SIMULATION は「盤面」｜「状況・入力・結果」。
  他の候補が無いときは 1 列のまま読みやすい幅に制限する。詳細は `docs/DESIGN_SYSTEM.md` 7 節。
- Darts Calculator の**UI デザインはコピーしない**。SVG ダーツボードの技術実装のみ再利用する。
- 重要情報を長文で埋めない。理由は **短い要約 → 詳細を開く**（progressive disclosure）。
- 過度なアニメーションは入れない。スマートフォンでの速度・視認性を優先する。

## 2. 共通

### ヘッダー

アプリ名（押すとトップへ）／モードの切り替え／「設定」ボタン。
64rem 未満では 1 段目にアプリ名と設定、2 段目にモードの切り替えを横幅いっぱいで置く。
64rem 以上では 3 つを 1 行に並べる。

### フッター

`© 2026 Chihiro Hashimoto` のみ。データの出処や免責の説明は置かない。

### ナビゲーション

`CHECKOUT` / `SETUP` / `TRAINING` / `SIMULATION` の 4 つ。`aria-pressed` で選択状態を示す。
凹んだ溝の中で選んだものだけが反転するセレクタースイッチ。320px でも 4 つの名前を省略せずに出す。

### StatusBar

`LEFT`（3rem の大きな数字）と `DARTS`（残り本数 + ピップ表示）。
BUST / CHECKOUT! の状態表示と、補足メッセージ（ノーテン警告、TON トラップ警告など）。

CHECKOUT / SETUP では**実戦入力を開いているあいだだけ**出す。通常表示では
残り点が入力欄に出ているので、答えの手前に同じ数字をもう一度置かない。
盤面をたたんでいるあいだの補足メッセージは、LEFT 入力の直下に 1 行で出す。

### Safe Area（iOS の PWA）

ホーム画面から起動した iOS の PWA は `apple-mobile-web-app-status-bar-style: black-translucent`
で表示する。暗い配色との一体感を保つためにこの設定は変えない。
その代わり、Web コンテンツがステータスバー（時計・電波・バッテリー・Dynamic Island）や
ホームインジケーターの下まで広がるので、**アプリ全体の余白**として
`env(safe-area-inset-top / right / bottom / left)` を `.app` の 4 辺の padding に足す。

- header だけに margin を足すような場当たり的な対応はしない。
- 横画面ではノッチが左右に来るため、left / right も必ず考慮する。
- `env()` は通常のブラウザや Android で 0 になるので、そちらの見た目は変わらない。
  非対応ブラウザでも余白が消えないよう、ショートハンドの `padding` を先に宣言してから
  4 辺を上書きする。
- `index.html` の `viewport-fit=cover` が前提。これが無いと inset は常に 0 になる。

構造は `src/App.safeArea.test.ts`（CSS の宣言の形）と `e2e/app.spec.ts`
（通常ブラウザでの算出値と横スクロールの有無）で回帰テストしている。

## 3. CHECKOUT / SETUP 画面

「103 のアレンジを確認したい」という普段の使い方で、答えの手前に大きな盤面を
通過させない。上から順に:

1. **残り点の入力（LEFT）** — この画面の主操作。`inputMode="numeric"` の大きな入力欄
   （数字は 2rem 以上、モバイルでは横幅いっぱい、`:focus-within` で枠を強調）と、
   `残り点 LEFT` ラベル + 短い補足（`2〜170・この3投で上がる` /
   `171〜350・次の3投に向けて整える`）。
   **確定ボタンもプリセットも置かない**（詳細は `docs/SPEC.md` 3-1）。
   初期状態は空欄で、`例 103` / `例 302` の placeholder だけを出す。
2. **STANDARD（CHECKOUT）／ BEST（SETUP）** — 基準ルート／最善のセットアップ。
   理由は既定で開いている。SETUP では `取得 138 点 → 残り 164` を添える。
   CHECKOUT の 42 / 46 / 48 / 39 / 43 だけ、STANDARD カードの直下に
   **「盤面の狙い方」**カード（`AimAreaCard`）を置く。既定はたたみ、Bust する的が
   あるとき（48 の T16、39 の T17・T19・D19、43 の T19）だけ、その注意を
   たたんだままでも 1 行で見せる。詳細は `docs/SPEC.md` 4-1-1。
3. **`実際の着弾を入力`** — 実戦入力（Recovery）の開閉ボタン。
   英語の `Recovery` だけを主ボタン文言にしない。
4. **MY ROUTE** — 得意ダブルを反映した候補（STANDARD と同一なら出さない）
5. **OTHER ROUTES** — 上位 5 件 →「さらに 40 件表示」で段階的に増やす／
   「すべて表示」で全件。ボタンに出す件数と実際に並ぶ件数は必ず一致させる。
   SETUP では BEST を除いた 2 件目以降が並ぶ。

### 実戦入力（Recovery）

**通常表示では展開しない。** `実際の着弾を入力` を押したときだけ、STANDARD / BEST の
直後に開く。開いた状態は同じ画面にいるあいだ保つが、LEFT を別の残り点へ書き換えたら
新しい3投として初期化する（たたんで、投げた記録も消す）。

開いたときの中身は、盤面を見たまま完結するようひとまとまりにする。

1. **StatusBar** — 現在の残り点 / 残り本数 / BUST・CHECKOUT
2. **SVG ダーツボード** — 実際に刺さった場所をタップして記録
3. **NEXT 表示** — 盤面の直下。`84 LEFT / 2 DARTS` と、次に狙うルート（`T20 → D12`）を
   コンパクトに出す。「外れた → 次どこ？」を即答するのが役割なので、理由は重複させない
   （理由は上の STANDARD / BEST カードに残す）。**`1投戻す` もここに置く**
   （誤タップの訂正で盤面から離れないため。Undo はアプリ内でここ 1 か所だけ）。
4. **VisitTrail** — この3投の記録と、`次の3投へ` / `最初から`

ルートのチップを押したときは、たたんでいれば実戦入力を開き、**盤面が見える位置まで
移動してから**そのセグメントを強調する。チップは MY ROUTE や OTHER ROUTES など
盤面より下のカードにもあるため、移動しないと開いた盤面が viewport の上へ出てしまう。
すでに開いている（盤面が見えている）ときは動かさない。

入力完了（Enter / Done・blur）で予約した「答えへの移動」は、その待ち時間のあいだに
ユーザーが実戦入力を開いたりルートのチップを押した場合、**取り消す**。
ユーザー自身が選んだ行き先を、あとから割り込んで上書きしない。

### RouteCard

- ルートは `T19 → S6 → D20` のようにチップで表示。**チップを押すと盤面で位置を確認できる**。
- 右上に推奨度バッジ（S / A / B / C）。スクリーンリーダーには意味も読み上げる。
- 要約は 1 行（書き下ろし説明があればそれ、なければ最初の理由）。
- `理由を見る` / `理由を閉じる` で詳細を開閉する。理由は極性で色分けし、
  色に加えて `+`（強み）/ `−`（注意）の記号を置く。
- 区画の見出しは日本語の文で置く（`基準ルート` / `次ラウンドの残しを作る` /
  `次ラウンドへ整える` など）。札（`STANDARD` / `BEST` / `NEXT VISIT`）はカードの中に置く。
- OTHER ROUTES は 1 枚のパネルを罫線で区切った一覧にし、推奨度の札を各行の右端でそろえる。

## 4. TRAINING 画面

1. **モード選択** — CHECKOUT / SETUP / RECOVERY / MIXED
2. **詳細設定**（折りたたみ）— 出題範囲 / 出題数（10・30・無限）/ 制限時間 / 苦手優先
3. **開始ボタン**
4. 出題 — StatusBar に残り点と本数、設問文
5. **SVG ダーツボード** — 狙う場所を順にタップ
6. **回答欄** — 3 枠。操作は `1投戻す` / **`回答する`** の 2 つ。
7. **採点結果** — 成立可否、推奨度、あなたの回答（理由つき）、より良いルート。
   その**直下に `次の問題`** を目立つ形で置く（結果を読み終えた位置から探させない）。
   回答前には出さない。同じボタンを上下 2 か所に置かない。
8. **学習履歴** — 回答数 / 正答率 / 平均回答時間 / 連続正解 / 非推奨選択、
   ランク別・スコア帯別・上がりダブル別の表、履歴消去

**自動確定はしない。**「回答する」を押すまで採点しない。

## 5. 設定画面

- **MY ROUTE の得意ダブル** — 順位つきリスト（↑ ↓ × で並べ替え・削除）と、
  D1〜D20 + BULL の選択グリッド
- **基準ルートについて** — 一般ユーザー向けの短い説明のみ。
  データの出処や件数、レビュー状態といった開発内部の情報はユーザー画面には出さない
  （`docs/CHECKOUT_DATA_POLICY.md` と `docs/APPROVALS.md` で管理する）。

## 6. 配色

Dark を既定にし、Settings で Light / Dark を明示的に選択できる。選択は既存の
preferences storage に保存し、再読み込み・PWA 再起動後も維持する。System 選択肢は置かない。
テーマ変更時は document の color scheme と `theme-color` も同期する。

色・surface・border・shadow・focus は `src/index.css` の semantic CSS token で一元管理し、
各コンポーネントへテーマ固有色を直書きしない。Dark はグラファイト、Light はアルミを基調とし、
主操作は反転（Dark: チョーク色の面 / Light: インク色の面）で示す。色は推奨度・判定・盤面など
意味のある所にだけ使い、盤面の色は実際のダーツボードに合わせる。規則は `docs/DESIGN_SYSTEM.md`。

## 7. アクセシビリティ

- 全区画に `aria-label`（例:「トリプル20、60点」「ブル、50点」）
- `role="button"` + `tabIndex` + Enter / Space で盤面をキーボード操作できる
- タップ領域 44px 以上（`min-height: 2.75rem`）
- `:focus-visible` で 2px のフォーカスリング（offset 2px。Dark はチョーク色、Light はインク色）
- 採点結果は `aria-live="polite"`、制限時間は `role="timer"`
- `prefers-reduced-motion: reduce` でアニメーションを無効化

## 8. アプリの更新のお知らせ

Service Worker が新しいビルドを見つけたとき、**勝手にリロードしない**。
画面のいちばん上へ「新しいバージョンがあります。」のお知らせを出し、
更新するかどうかをユーザーが決める。

- 表示位置は上部（sticky）。スクロールしていても気づけるようにする。
  iOS の PWA でステータスバーへ潜らないよう `--app-safe-top` を使う。
- **更新** … 待機中の Service Worker へ切り替え、そのまま読み込み直す。
- **閉じる** … お知らせだけを消す。更新は待機したままで、
  次にアプリを開き直したときか、さらに新しいビルドが待機したときに再び尋ねる。
- TRAINING の回答中・SIMULATION のゲーム中でも表示する。
  押すまで何も起こらないので、進行中の状態は失われない。

実装は `registerType: 'prompt'` と `workbox.skipWaiting: false`
（`vite.config.ts`）＋ `src/pwa/updateStore.ts` / `src/components/UpdateBanner.tsx`。

`clientsClaim` は `true` のまま。これは初回にインストールされた Service Worker が
すでに開いているページの制御を引き取るかどうかで、更新の待機とは別の話。
`false` にすると初回訪問がリロードまでオフラインで動かなくなる。

以前は `registerType: 'autoUpdate'` で、新しいビルドを検出すると
`window.location.reload()` が走っていた。TRAINING の回答途中でも読み込み直されるため、
ユーザーへ尋ねる形へ変更した。

この変更自体は **`src/data/versionHistory.ts` へ載せない**（オーナー判断 2026-09-22:
サイレントアップデートで構わない）。1 PR = 1 エントリの慣習の例外なので、
抜けと勘違いして追記しないこと。`src/VersionHistory.test.tsx` で固定している。
